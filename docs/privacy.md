# What temet-work stores and sends

<!-- Reference, not reassurance: one plain sentence per fact, no stacked "never"/"only". -->

## Where it sends data

| To | What | When |
|---|---|---|
| GitHub, through `gh` | Reads issues, open milestones with their due dates, pull requests, whether each is a draft, each one's branch, and their CI, and the workflow runs of a merge commit; comments on, closes and reopens issues; creates each issue an investigator files (`gh issue create`, with its title, text and milestone); sets an issue's title for a person's refine (`gh issue edit KEY --repo NAME --title TITLE`); merges pull requests by the `merge` setting (`--squash` unless set otherwise) | Issues and milestones at every sync, every 60 s by default (`sync_every`); a pull request every 30 s while it is in review, and a merge commit's runs every 30 s while the next repository waits for them; comments, closes and merges when the loop calls for them; a reopen after a failed verify, at once and at each sync until the issue is listed as open; an issue when an investigator runs `temet-work file`; a title when a person runs `temet-work refine --title`, or saves a changed title in the window's Refine dialog |
| GitLab, through `glab`, for a project whose `code_host` is `gitlab` | Reads merge requests, each one's source branch, their pipelines and jobs, and the pipelines of a merged commit; merges merge requests | A merge request every 30 s while it is in review, and a merged commit's pipelines every 30 s while the next repository waits for them; merges when the loop calls for them |
| Jira Cloud, through `curl`, for a project or area whose tracker is `jira` | Searches the open issues (summary, description, fix versions, links, status) and checks the status of the issues they depend on; reads the project's fix versions with their release dates, and searches the open issues again to count each version's; comments on issues; runs the transition to Done, and the first transition out of Done for an issue whose verify failed; creates each issue an investigator files, as a Task with its summary, description and fix version; sets an issue's summary for a person's refine, with a PUT of `fields.summary` to `/rest/api/3/issue/KEY`. It signs in over HTTPS with `JIRA_USER` and `JIRA_TOKEN` from the daemon's environment, gives the token to `curl` on standard input, and does not store either | Issues and fix versions at every sync, every 60 s by default (`sync_every`); comments and transitions when the loop calls for them; the transition out of Done after a failed verify, at once and at each sync until the issue is listed as open; an issue when an investigator runs `temet-work file`; a summary when a person runs `temet-work refine --title`, or saves a changed title in the window's Refine dialog |
| herdr-core, over its local socket | Starts, reads, sends text to and stops agents' terminals, on this machine or on another machine herdr-core knows, with each agent's brief and environment, which holds the agent's secret (`SECURITY.md`). herdr-core passes the environment to the other machine for an agent there. Each terminal is labelled with `owner=temet-work` and with `program`, the first word of the program it runs (`claude`), and each agent's terminal also with the agent, group, role and event log, and with the issue it works on. An agent's terminal also gets `herdr.space` (made from the group), `herdr.tab` (from the group and issue) and `herdr.name` (the agent and issue), so the herdr app shows it: one space per group, one tab per issue. An investigator works on no issue: its tab is made from the group and its role, and its name from the agent and group. For a work folder on another machine it also runs `temet-work trust-folder RUNTIME PATH` there, with `CLAUDE_CONFIG_DIR` when the daemon has it | Every 2 s, and with each command; the trust command before each agent starts on another machine |
| Anthropic or OpenAI, through the Claude Code or Codex sessions it starts | What Claude Code or Codex itself sends, including the agent's brief. An author's brief on an issue with pull requests gives each one's project, repository, number and branch, and the number and branch of one a person closed without merging. A reviewer's brief, an arbiter's brief and a running reviewer's next-round message give the same for each pull request that is not closed. Review points and the author's replies go in briefs and in the messages to running agents: a reviewer's brief and next-round message hold the points of the round before with the author's reply to each, an author's brief and fix message the points of the block its ready answers, and an arbiter's brief the latest review round of the issue and as many earlier rounds as fit in the room the rest of its brief leaves, with each point, the author's reply to it and its state, and a count of the earlier rounds, which `temet-work issue` still holds. Every brief, next-round message and fix message is held to 100 KiB: each check, kept rule, point and reply is cut to its first 1,000 characters, with a pointer to `temet-work issue` (for a rule, `temet-work status`), and those that still do not fit are counted on a line instead (`docs/commands.md`, "What a brief holds"). The checks a person gives an issue with `temet-work refine` go in its refiner's, author's, reviewer's and arbiter's briefs, cut and counted the same way, and a refiner's brief on an issue a person sent back holds the checks of the plan it replaces. A kept rule is in every brief on every project, as many of the latest as fit, with a count of the others, and a project's `investigate` setting is in every investigator's brief for its group. Each investigator's brief also holds the ids and titles of the issues a person closed in its group's projects and areas | While an agent runs |
| The daemon's machine, over your own `ssh`, from an agent on another machine | Each `temet-work` command the agent runs (a plan, a review, a ruling, a choice) goes to the daemon's socket through `temet-work relay`, with that machine's `temet-work` build and its name (`uname -n`) and the agent's secret, and the reply comes back. The relay asks the daemon its build, and a refusal for another build brings that build back to the agent's machine. Nothing listens on a port | While an agent on that machine runs |
| Whoever runs `temet-work status --json` on the daemon's socket, or through `temet-work relay` from another machine, and the desktop app over the daemon's socket | The state as JSON: projects and their areas, milestones, groups, the issues that are not done with their pull requests, the count of done ones, agents, decisions and problems. It carries what no text form does: when each issue last changed; whether each issue's review approved and its checks passed; each issue's plan checks with each one's state (`passed`, `running`, `waiting` or `failed`), and the checks a person gave it with `temet-work refine` (`person_checks`, each a done-when and a proven-by); its review rounds with each round's reviewer and verdict and each point's text, the author's reply to it and its state (`open` or `resolved`), written as `null` where the log holds none, as in a log from before states were kept (of the rounds, `temet-work issue` prints all but the reviewers); each agent's group, work folder id, start number, and the runtime and model it was started with; each milestone with how many of its issues are done and in all, and its due date; the web addresses of each project's issues and code and of an area's issues, made from the names in `config.toml` and the daemon's `GH_HOST`, `GITLAB_HOST` and `JIRA_URL`; and whether a person has held the daemon, with the time the hold began. It leaves out agents' secret digests, the usage-limit reset times the daemon reads, folder paths and settings, and also issues' own text, a plan's settings and repositories, what an author is to fix, rules and the waiting list. Problem lines and agents' state lines are sent as `status` prints them, except for work folders' paths: the lines for blocked and errored agents leave the folder out, and a path in any other of these lines is written as `folder` and the folder's id (a path that is a bare name, such as `work`, only after "cannot trust"). Whatever else such a line holds is sent, including a reset time in an agent's own words, another path, or a deploy command's output. Review points, the author's replies, plan checks and a person's checks are treated like problem lines and agents' state lines: a work folder's path in them is written as `folder` and the folder's id (a path that is a bare name only after "cannot trust"), and any other path in them goes out as written. Titles and decisions are sent as their authors wrote them | When the command is run; a request that names an agent needs that agent's secret, as for `status`. The desktop app asks as a person, one second after its last ask ended, while it runs |
| A project's `deploy` and `verify` commands | Whatever those commands send; temet-work runs them with `sh -c` | After a merge, and after a deploy |
| Nothing else | No telemetry. The daemon has no network client of its own. | |

The daemon keeps each open issue's text from its tracker's last sync in memory, and the text of
an issue that is merging, deploying, being verified or waiting to be reopened after a failed
verify from the last sync that listed it. It prints that
text to whoever runs `temet-work issue` for the issue, or calls the MCP server's `issue` tool.
It does not write the text to `events.jsonl`. The same reply holds all the issue's review
rounds: each point, the author's reply to it and its state. An arbiter's brief holds the latest
of those rounds always and the earlier ones that fit in the room its other parts leave under
100 KiB, with a count of those it leaves out, and cuts each point and reply to 1,000
characters. Unlike `status --json`, the reply and the brief hold the words of each point and
reply as they were stored, with any work folder's path in them, print no control character,
and indent their later lines. An agent that runs the
command sends the text and the rounds to Anthropic or OpenAI as part of its session.

Each agent gets `TEMET_WORK_AGENT`, `TEMET_WORK_AGENT_TOKEN` (a random secret of its own,
`docs/commands.md`), `TEMET_WORK_DAEMON` when it is on another machine, and these from the
daemon's environment when they are set: `CLAUDE_CONFIG_DIR`, `HTTPS_PROXY`, `NO_PROXY`,
`NODE_EXTRA_CA_CERTS`, `GITHUB_TOKEN` and `GH_TOKEN` (`SECURITY.md`).

On Linux the daemon reads the environment of the process that sent a command, and of that
process's parents, from `/proc`. It takes the `TEMET_WORK_AGENT_TOKEN` values it finds,
compares their SHA-256 digests with the ones it recorded, and keeps nothing it read.

## Where it writes files

| Where | What | Moved by |
|---|---|---|
| `~/.config/temet-work/` | `config.toml`, which temet-work reads at start and does not write | `XDG_CONFIG_HOME`, or `temet-workd --config FILE` |
| `~/.local/state/temet-work/` | `events.jsonl`, the event log. It holds the issues, plans, review points, rulings, the choices agents record (the question, the options, the one taken, why, the cost to undo, the point and the agent that chose), a person's overturn reasons and the rules made from them, and each person's refine: the issue, the title written to its tracker when it changed, the person's checks when given, and whether it was sent to a refiner. Plan checks, a person's checks, review points, the author's replies, rulings, choices and overturn reasons are stored with every control character dropped but the line feed and the tab, and with each other line break (a carriage return, NEL, U+2028 and U+2029) stored as a line feed. It also holds the text `gh` or `glab` returns when it refuses a merge, each pull request's branch as its code host reports it (logged the first time a read finds it and again when it changes), the repository and number of each pull request a person closed without merging, as a read in review or the merge found it, the output of each verify command, the SHA-256 digest of each agent's secret, the line an agent's turn ended on when it ended in an error, with the reset time that line gives; whether an agent that ended had lost its program, as to a reboot; each investigation: its group, investigator and start time, each issue it filed (its id, title and milestone), and its end time with how many issues it filed; the runtime and model each agent was started with; the author's reply to each point of a review block, sent with the first ready after it; each plan check's state as the loop learned it: waiting in the plan, and in each verdict the checks the reviewer found do not hold (the others passed), with running and the return to waiting following from the author's ready and a change sent back; and in each verdict the points of the round before that it kept open (the others resolved); each milestone its tracker lists as open, with its due date, logged when it is first listed, when its due date changes and when the tracker stops listing it; each ruling's and each choice's cost to undo and its point; and each time a person held or resumed the daemon. Each entry has the time it was logged, from which the daemon works out when each issue last changed. The web addresses are not in it: the daemon makes them again from the configuration and its environment. `deploy-handoff` holds the issue and build of a deploy that restarts the daemon. `deploy-handoff.stale` holds, for each deploy run again because the daemon that came up was another build, the issue, the build installed and the build running | `XDG_STATE_HOME`, or `temet-workd --log FILE` |
| `$XDG_RUNTIME_DIR/temet-work/` | `daemon.sock`, the daemon's socket. It is in `~/.local/state/temet-work/` when `XDG_RUNTIME_DIR` is not set, as on a Mac | `TEMET_WORK_SOCKET` |
| Standard error | A line for each request that changes something, `request: by=AGENT COMMAND -> done`, and for each refused request, `-> refused: REASON`; none for a `status`, `view`, `issue`, `screen` or `settings` request the daemon answers. Also a line per new problem, a line per agent started (`started: AGENT on MACHINE in FOLDER (terminal T)`), and before it, for a folder on another machine, `trusted: FOLDER on MACHINE, for AGENT`. A stop of an ended agent's terminal that fails gives `cannot stop AGENT's terminal T: REASON; trying again in a minute`, once per try. While a stop after an agent's last reminder keeps failing, the runner's problem lists `cannot stop AGENT's terminal T: REASON`, with the reason from the latest try: it is sent in `status` and to the desktop app, and printed here once as a new problem (`problem: runner: …`), and again only when the runner's problem line changes. While a stop the loop asked for keeps failing, as after a merge or a close in the tracker, Problems lists `stop AGENT` with the reason the runner family gave the last time the loop asked for that stop: it is sent in `status` and to the desktop app, printed here as `problem: stop AGENT: REASON` when it first fails and again when that reason changes, and dropped once the agent has ended, whatever ended it. The loop asks each round for the stop of an agent whose step is over for good, so its line follows the latest try; any other line keeps its first reason. Such a stop is tried again once a minute, and the tries print no line of their own. Under systemd it goes to the journal | |
| `~/.claude.json`, Claude Code's user file, on the daemon's machine and on each other machine a work folder is on | `projects.<folder>.hasTrustDialogAccepted` for each work folder on that machine, so a Claude Code agent does not stop at the folder-trust question. On another machine `temet-work trust-folder` writes it there. Nothing else in the file changes | `CLAUDE_CONFIG_DIR` |

## Removing it

Uninstall with `cargo uninstall temet-work`. Then delete `~/.config/temet-work/` and
`~/.local/state/temet-work/` to remove its data. The trust entries in `~/.claude.json`, on
each machine a work folder was on, stay until you remove them. The agents it started run in herdr-core terminals labelled
`owner=temet-work`, and keep running until you stop them. Each also carries `herdr.space`,
`herdr.tab` and `herdr.name`, so the herdr app shows it in its group's space, in its issue's
tab, or for an investigator in a tab of its own. A herdr app that shows a terminal turns
herdr-core's `keep` on for it and adds a `where` label (`docs/findings/herdr-core.md`,
Labels).
